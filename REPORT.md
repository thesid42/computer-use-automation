# Design Report

## Architecture

The system is a local Automation Companion that accepts a natural-language goal and operates a separately deployed back-office application through its visible UI. The repository contains two independent applications: legacy-demo/, a synthetic early-2000s-style member-servicing workstation, and companion/, the workflow workspace and runtime. They have separate packages and processes. The companion does not import demo code, read its data, call a hidden business endpoint, or rely on target-specific automation hooks. The target integration is browser-only; the companion's own /api routes are local internal routes for its workspace and workflow library.

The companion contains a Goal Controller, LLM discovery runner, durable workflow library, deterministic replay runner, policy gate, evidence store, and human-control lease. A natural-language task matches an active compatible workflow when possible. A miss begins discovery against the configured target. The New automation dialog starts that path. The Automations detail view exposes the selected workflow's typed inputs and direct run form.

The library stores durable metadata for multiple workflow records: ID, title, description, archive state, timestamps, and a link to the executable artifact. The current main runtime is seeded with one savings-balance workflow; multi-workflow storage and API behavior are covered by local tests rather than presented as three pre-seeded records. The artifact and run evidence stay in separate runtime namespaces. This separation lets an operator edit description or archive state without rewriting recorded actions, and lets startup restore metadata and terminal run summaries without claiming an interrupted browser session can resume. GET /api/workflows, GET/PATCH /api/workflows/:id, and POST /api/workflows/:id/runs form the internal library seam. The direct run route validates typed inputs and invokes replay with zero model decision calls.

The implementation is deliberately bounded to three read-only workflow families on one synthetic target: savings balance lookup, savings transaction history filtering, and loan payoff quote. The library is broader than the target adapter's current intent coverage so the product can retain compatible future artifacts without claiming generic automation support. The repository retains sanitized historical provider-backed discovery and replay evidence under evidence/. That evidence is preserved as historical core-slice evidence; current expanded-flow and library verification is left to the final checkout commands in MVP-ACCEPTANCE.md.

## Artifact schema

A successful discovery produces a schema-validated, versioned capability rather than a model transcript. It contains a capability ID and semantic version, intent signature, typed inputs and outputs, expected business outcomes, risk and policy profile, ordered actions, locator strategies, preconditions, postconditions, waits, bounded retries, extraction rules, final checkpoint, and target compatibility.

The three workflow families use explicit typed inputs. Balance lookup takes a member identifier. Transaction search takes a member identifier plus ISO start_date and end_date. Loan payoff takes a member identifier and ISO as_of_date; the current target artifact records the rendered Auto Loan or Personal Loan choice as a visible, fixed step in the learned flow. Inputs remain references in actions, such as fromInput: member_id or fromInput: as_of_date. Concrete member values and dates are supplied fresh for each run and are not saved into artifacts or library metadata. Outputs are typed balance/quote money or the rendered transaction result, with declared outcome codes for empty and invalid cases.

Targets contain an ordered set of strategies: accessible role/name, associated label, visible text, text-relative structure, frame path/URL, constrained fingerprints, or visual anchors when an adapter implements them. The Playwright adapter resolves the browser strategies used by this target and requires an unambiguous match. The artifact is decoupled from the raw model transcript and from any one tenant's concrete input values.

## Determinism & error handling

Direct workflow runs and matched natural-language replays use the saved artifact without an LLM deciding actions. The runner validates the artifact and input object, confirms automation owns the session, checks a precondition, resolves the target using fixed strategy order, applies policy, performs the primitive action, waits for the declared condition, verifies the postcondition, checks declared outcomes, extracts outputs, and verifies the final checkpoint. An API response includes a run ID and typed result; direct runs carry llmCalls: 0.

The result contract distinguishes success with checkpointVerified: true, a business_outcome, needs_human, and failed with structured error detail. MEMBER_NOT_FOUND and PERMISSION_DENIED are caller-relevant target outcomes. Transaction search returns NO_TRANSACTIONS for a valid empty range and INVALID_DATE_RANGE for malformed or reversed dates. Payoff quote returns NO_LOAN, INVALID_AS_OF_DATE, or UNSUPPORTED_AS_OF_DATE as appropriate. The target's 77777 fixture demonstrates one bounded transient search retry. Ambiguous or missing targets, unexpected dialogs, exhausted recovery, checkpoint mismatch, parse errors, browser failure, invalid invocation, and policy violations stop with the step, expected state, observed state, and evidence reference.

Discovery uses temporary references from each observation; it does not hand persistent model selectors to replay. The same action schema, policy checks, and surface seam are used for discovery and replay. The current code's local scripted mode validates this control flow without a provider key, while the preserved evidence package demonstrates the original genuine discovery/replay seam. A separate [savings runtime verification summary](evidence/savings-runtime-verification.json) records five direct replay/handoff scenarios and one restart persistence check with zero model decision calls; it is runtime verification rather than new provider-backed discovery and does not establish the expanded-flow results. Frozen local validation reports 21/21 legacy target tests, 71/71 companion tests, passing root typecheck and build, and 2/2 scripted browser workflow tests. No new workflow family completed reliable genuine provider discovery: the first transaction JSON run failed after 16 calls at the progress bound, the tool-retry transaction run failed after 2 calls on unsupported or missing tool-call output, the loan JSON run reached Loan Accounts after 8 calls before a 60-second timeout, the final transaction JSON run reached 12 calls before malformed action repair failed, and a same-Nano standard-route attempt returned HTTP 404 after one call. The transaction and loan flows therefore remain locally scripted-test verified rather than provider-verified; savings retains the genuine historical provider evidence.

## Heterogeneity & multi-tenant

The SurfaceAdapter separates how a computer is perceived and acted on from the recorded flow. Playwright is the implemented browser adapter. A legacy web adapter could map frame paths, visible text, accessibility controls, or visual anchors to server-rendered pages. A desktop adapter could map the same action contract to Windows UI Automation or macOS accessibility APIs. The artifact does not assume a clean DOM or a target API.

At scale, a workflow record would be scoped to an application family, tenant policy, and version. A tenant profile would supply base URL, branding aliases, detected version fingerprints, permissions, and narrowly scoped locator overrides. A shared artifact is selected only when the surface fingerprint is compatible. Drift creates a review or specialized version and is surfaced as an explicit failure; it does not silently mutate a shared capability. This repository implements one target profile and three read-only workflow families. Tenant registries, cross-tenant rollout, desktop support, and per-tenant infrastructure are design seams rather than delivered claims.

## Escalation & handoff

Discovery or replay opens an intervention when it cannot safely continue, encounters the supervisor-verification fixture, reaches an unknown state, or exhausts bounded recovery. The runner pauses, captures the current target screenshot, and records the run, workflow, current step, reason, observed context, and control owner. The Needs attention page makes the intervention visible with Take control, Continue automation, and Abort actions.

Take control transfers an explicit lease from automation to the human and rejects further automation actions. The existing headed target browser page is brought forward, preserving cookies, navigation, form state, and the live session. The operator can submit the visible supervisor acknowledgement or otherwise correct the page. Lightweight click/change/navigation events are recorded with sensitive values redacted. Continue transfers the lease back, captures a fresh observation, and resumes from the same session. Abort closes it and records an aborted run. The local screenshot/operator surface is intentionally minimal; real-time remote co-browsing is out of scope.

## Safety

The same policy gate protects discovery, typed direct replay, and natural-language matched replay. It allowlists origins and route patterns, action kinds, a maximum risk class, and the current control owner. Actions are classified as READ_ONLY, REVERSIBLE_WRITE, or IRREVERSIBLE_WRITE. All three delivered workflow families are read-only. The visible Post Fee control in the target is a policy-denial fixture and cannot be used to post a write.

The target contains synthetic records only. Provider keys belong in ignored .env files and are sent only in the authorization header. Keys are not written to artifacts, workflow metadata, screenshots, JSONL events, summaries, or prompts. Operational member identifiers and entered input values are redacted from user-facing activity; the requested transaction result intentionally retains its business dates so the operator can verify the filtered ledger. Artifacts keep input references. The target has no hidden API seam, and the companion cannot bypass the visible workflow. Production identity, encrypted retention, and enterprise audit controls remain future work.

## Cuts

The assignment prioritizes a complete vertical slice over breadth. The MVP intentionally leaves out real bank integrations, target API integrations, irreversible financial actions, desktop automation, a second tenant or variant, cross-tenant rollout infrastructure, distributed queues/workers, production authentication/RBAC, a public capability catalog, generated code, formal confidence/approval lifecycle, and open-ended LLM recovery during replay. The target adapter supports three named read-only workflow families and does not claim arbitrary member-servicing task coverage.

The workflow library, archive/restore metadata, detail input form, searchable history, and same-session handoff are implemented at the local product seam. Further work would add a second surface variant to exercise tenant overrides, a desktop adapter, encrypted/expiring evidence retention, stronger visual-anchor resolution, and production operator transport. The local validation listed above is complete. Fresh provider discovery of the expanded workflows was not reliable in the recorded attempts, so the report makes no provider-verified claim for those families.
